## 1. Цели и предпосылки
### 1.1. Зачем идем в разработку продукта?
**Проблема:** Преподавателей и ассистентов на курсе зачастую мало, а автопроверка отвечает только «Wrong answer on test 7». Обычные LLM-чаты выдают готовый код, и студент не учится.
**Цель продукта** - Разработать интеллектуального наставника по программированию, который помогает студентам находить и исправлять ошибки в собственных решениях с помощью последовательных подсказок, не предоставляя готовый исправленный код. При самостоятельном решении задач по программированию студент может испытывать трудности с определением причины неверного результата.

**Что даёт ML:** LLM позволит решать любые задачи предлагаемые студентом в формате Наставника. Существующие ИИ-ассистенты способны предлагать готовые исправления, однако это не всегда способствует самостоятельному освоению навыков отладки и пониманию алгоритмов.

**Успех итерации:**  Прототип, позволяющий провести воспроизводимую оценку качества автоматического выявления ошибок и генерации образовательных подсказок. Также успех будет определяться в зависимости от показателей метрик (подробнее о границах метрик в Этапе 2 разделе "Метрики" п. 2.3). К сожалению на первом этапе реализации проекта не предусмотрен пилот/тестирование на реальных пользователях, поэтому качество подсказок (как хорошо студент выполняет задание после подсказки) отследить невозможно. Будет произведена "легкая" ручная проверка разработчиками для определения очевидных ошибок (проверить что система не оценивает очевидную утечку ответа в подсказке, как подсказку без утечки) на небольшом пуле.


### 1.2. Бизнес-требования и ограничения
* **Требования:**
    1. Пользователь может отправить условие задачи и исходный код решения на Python. Система должна иметь возможность использовать доступные тесты для проверки решения в изолированной среде.
    2. Система проверяет решение на тестах, определяет результат выполнения и при обнаружении ошибки формирует описание её предполагаемой причины.
    3. Система предоставляет подсказки трёх уровней конкретности: от общего направления поиска ошибки до более точного указания на проблемный участок логики.
    4. Подсказки должны помогать студенту самостоятельно находить и исправлять ошибки, не раскрывая готовое исправленное решение в стандартном режиме наставничества.
    5. Пользователь может отправить исправленную версию кода для повторной проверки. Система учитывает историю попыток и ранее предоставленные подсказки в рамках текущей сессии.
    6. Качество диагностики и подсказок должно поддаваться воспроизводимой оценке и сравнению с простым бейзлайном.

* **Ограничения:**
    * Ограниченные вычислительные ресурсы и бюджет учебного проекта.
    * Ограниченный объём ручной разметки для оценки качества.
    * Первая итерация ограничивается задачами на Python, для которых доступны условия и пригодные для выполнения тесты.
    * В первой итерации используются готовые LLM без дообучения весов. Полноценная персонализация, автоматический подбор задач и проверка долгосрочного образовательного эффекта не входят в обязательный объём Первой итерации.

### 1.3 Что входит в скоуп итерации

* **Входит в MVP**
    * Поддержка одного языка программирования: Python.
    * Работа с условием задачи, исходным кодом и тестами.
    * Классификация типичных ошибок студента.
    * Генерация подсказок с несколькими уровнями конкретности.
    * Базовая проверка подсказок на утечку готового решения.
    * Сохранение истории взаимодействий и категорий ошибок.
    * Офлайн-оценка качества на фиксированном наборе задач.
* **Не входит в MVP:**
    * Поддержка нескольких языков программирования.
    * Полноценная интеграция с LMS и образовательными платформами.
    * Обучение собственной большой языковой модели с нуля.
    * Сложная система пользовательских профилей и долгосрочной адаптации учебной программы.
    * Масштабирование на промышленную нагрузку.
    * Гарантия полного отсутствия ошибочных подсказок.

### 1.4. Предпосылки решения
1. Для значительной части учебных задач доступны эталонные тесты, позволяющие определить, является ли решение корректным.
2. Существуют открытые наборы программ с ошибками и соответствующими тестами, которые можно использовать для первичной оценки.
3. LLM способна извлекать полезную информацию из условия задачи, кода и результатов тестирования.
4. Успешное прохождение тестов является свидетельством корректности решения, но само по себе не доказывает, что студент понял причину ошибки.

## Методология
### 2.1. Постановка задачи
Code Mentor - интерактивная система помощи при отладке учебных программ. ML-компонент решает задачу условной генерации текста: на основании условия задачи, исходного кода, результатов объективной проверки и требуемого уровня конкретности генерирует подсказку, **не раскрывая готовое решение**. Дообучение моделей проводится **не будет**.

Определение того, проходит ли код студента тесты, не является прогнозом LLM: код запускается в изолированной среде (Judge0), а приложение агрегирует статусы и результаты тестов. Переходы между шагами заранее заданы, роутинг определяется программными правилами, а не решением LLM (AI Workflow). LLM-as-a-Judge используется офлайн для оценки качества подсказок.

Одна операция генерации - одна подсказка к одной попытке решения одной задачи на выбранном уровне конкретности подсказки. Система получает задачу и пользовательскую попытку -> после проверки кода, если есть ошибка, формирует подсказку. После следующей попытки цикл повторяется, при успехе система прекращает генерацию подсказок по данной задаче.

| Компонент / операция | Входные данные | Выход | Метод и ограничения |
| --- | --- | --- | --- |
| Sandbox | Код студента, Python runtime, тесты, лимиты ресурсов | `ExecutionResult`: число пройденных тестов, статус, безопасная сводка ошибок | Judge0 / аналог; изоляция и детерминированное сопоставление вывода с ожидаемым |
| Роутинг | `ExecutionResult`, состояние сессии | Следующий узел workflow | Программные правила: `accepted` -> завершение; ошибки решения -> диагностика/подсказка; `internal_error` -> техническая ошибка без учебного вывода |
| LLM*: диагностика | Условие, код, сводка тестов | Структура `Diagnosis` с предполагаемой ошибкой и подтверждающими свидетельствами | Вызов готовой LLM; ответ проверяется по схеме Pydantic; возможны ошибки диагностики |
| LLM*: подсказка | Условие, код, сводка тестов, `Diagnosis`, уровень подсказки {1,2,3} | Текст подсказки | Готовая LLM без выдачи исправленного кода; уровень задаёт приложение |
| Оффлайн оценка | Подсказки, уровень, эталонная экспертная разметка | Метрики(Leakage Rate, Hint Level Compliance), контроль корректности подсказок | LLM-as-a-Judge + проверка его качества на вручную(?) размеченной выборке |

>\* Одна и та же LLM. Также на данном этапе приянто решение использовать всё ту же LLM для самопроверки: Модель будет сама себе делать запрос с вопросом "Является ли подсказка корректной? Соответствует ли она уровню?

Уровни подсказок:
* **Уровень 1** - общее направление поиска ошибки;
* **Уровень 2** - более конкретная область или логика, которую стоит перепроверить;
* **Уровень 3** - подробное объяснение причины, не содержащее готовый исправленный код.


**Метрики** .Основные офлайн-метрики:

Leakage Rate - доля подсказок, раскрывающих решение. минимизировать
```math
LeakageRate_l =
\frac{\text{Количество подсказок с утечкой }l}
{\text{Количество всех подсказок уровня }l}
```
>$LeakageRate_l → min$

Hint Level Compliance - доля подсказок, соответствующих заданному уровню. максимизировать
```math
Compliance_l =
\frac{\text{Подсказки, соответствующие уровню }l}
{\text{Все подсказки уровня }l}
```
>$Compliance_l → max$

### 2.2 Блок схема работы Ментора
**Блок схема разработки и исследования**
```mermaid
flowchart TD
    A["Подготовка данных: RunBugRun, EDA, проверка тестов"] --> B["Разметка ошибок и критериев подсказок"]
    B --> C["Бейзлайн: один вызов LLM"]
    C --> D["MVP: diagnose → generate_hint, sandbox"]
    D --> E["Офлайн-оценка обоих подходов на одинаковых задачах"]
    E --> F{"Критерии приёмки выполнены?"}
    F -->|Да| G["MVP готов к ограниченному пилоту"]
    F -->|Нет| H["Анализ ошибок, утечек и затрат"]
    H --> D
```

**Блок-схема Пользовательского опыта**
```mermaid
flowchart TD
    A["Код и условие задачи"] --> B["Запуск тестов в sandbox"]
    B --> C{"Результат тестирования"}

    C -->|Все тесты пройдены| K["Задача решена"]
    C -->|Есть ошибки| D["LLM: диагностика ошибки"]

    D --> E["Генерация подсказки"]
    E --> F["Проверка качества и утечки"]
    F --> G{"Подсказка безопасна?"}

    G -->|Нет| E
    G -->|Да| H["Подсказка студенту"]

    H --> I["Студент исправляет код"]
    I --> J["Повторная отправка решения"]
    J --> B

    K --> L["История ошибок и краткий отчёт"]
```

### 2.3. Этапы решения задачи

#### Этап 1. Подготовка данных
На данном этапе реализации проекта данные будут использоваться только для оффлайн оценки работы системы.

##### Источники и основные сущности

Приоритетный кандидат - [RunBugRun](https://github.com/giganticode/run_bug_run). RunBugRun - это APR датасет с более чем 700 тыс. исполняемыми buggy/fixed парами коротких программ взятых из [IBM Project CodeNet](https://github.com/IBM/Project_CodeNet) (а также [AlphaCode/CodeContests](https://github.com/google-deepmind/code_contests), [AtCoder](https://atcoder.jp/posts/21), [PIE4Perf](https://github.com/madaan/pie-perf)), написанных на 9 языках (C++, C, Python, Java, Ruby, JavaScript, Go, PHP, C#) ((Первоначально в планах использовать только Python)).

Состоит из сущностей:
* `tests` - хранит входные данные и ожидаемые выходные данные для проверки программ;
* `problems` - хранит текстовые описания задач;
* `bugs` - пары «багованный/исправленный» код;
* `evaluations` - прогоны оценки. Отслеживает запуски оценки (изначально пустая);
* `runs` - отдельные запуски тестов. Записывает результаты выполнения отдельных тестов (изначально пустая).
> Использование сущностей `evaluations` и `runs` в ходе разработки под вопросом.

**Целевые переменные для оценки:**

| Целевая переменная | Тип и разметка | Как используется |
| --- | --- | --- |
| `leak_label` | бинарная: `1` — подсказка раскрывает готовое исправление / существенную часть решения; `0` — нет | Расчёт Leakage Rate |
| `level_compliance_label` | бинарная: `1` — подсказка соответствует заданному уровню конкретности; `0` — нет | Расчёт Hint Level Compliance |

**Дополнительные источники данных**

Если на этапе разработке появятся непредвиденные проблемы в использовании данных из датасета RunBugRun, то будут использоваться резервные источники:
* IBM Project CodeNet - крупный мультиязычный датасет с [AIZU Online Judge](https://onlinejudge.u-aizu.ac.jp/home) и [AtCoder](https://atcoder.jp/) от IBM;
* Code4Bench - мультиязычный бенчмарк с данных с [Codeforces](https://codeforces.com/) для различных методов анализа программ.

> Все данные находятся в открытом доступе и не хранят в себе конфиденциальной информации. Каждый датасет содержит достаточное количество наблюдений для проведения оценки работы системы, даже в случае расширения функционала системы.


#### Этап 2 - Подготовка прогнозных моделей

##### **Метрики**
Формулы метрик приведены в разделе 2.1. На данном этапе разработке предусмотрены только метрици оценки качества генерации подсказки. Основные рисики, с которыми может столкнуться система:
1. **LLM дает посдсказку, которая прямым образом указывает на ошибку, и говорит как решить проблему.** Эта проблема рушит всю идею системы, ведь студент используя CodeMentor должен получать не просто правильный ответ, который он получил бы и в любых других источниках (простой запрос в LLM/посмотрев на решения других людей), а процесс обучения.
2. **LLM дает подсказку не соответствующую уровню подсказки.** Эта проблема мешает полноценному обучению. Студент, который просто допустил опечатку в коде, не нуждается в детальных объяснениях, система должна просто попросить студента перечитать код или сказать ему, что в коде имеются опечатки.

Основные офлайн-метрики, оцениваемые отдельно для каждого уровня l:

- **$LeakageRate_l$** = число подсказок уровня l с `leak_label = 1` / общее число оценённых подсказок уровня `l`. **Минимизировать**. Данная метрика отслеживает первую проблему. На самом деле мы можем смотреть эту метрику не только для каждого уровня подсказки, общий *LeakageRate* тоже несет полезную информацию. Для успеха Первой итерации проекта считаем верхней границей 5%*
- **$Hint Level Compliance_l$** = число подсказок уровня l с `level_compliance_label = 1` / общее число оценённых подсказок уровня l. **Максимизировать**. Данная метрика напрямую отслеживает вторую проблему. Для успеха Первой итерации проекта считаем нижней границей 85%*

>**Принцип измерения:** LLM-as-a-Judge выдаёт структурированные оценки и обоснование по фиксированной рубрике. Итоговые отчёты включают числители, знаменатели, доверительные интервалы при достаточном числе примеров.

**Дополнительные метрики:**
* End-to-end Latency p95 - 95-й процентиль времени от отправки кода до получения подсказки. Для успеха Первой итерации проекта считаем нижней границей 20 секунд*
* Workflow Correctness - метрика, показывающая, насколько правильно работает логика AI Workflow: выполняются ли нужные шаги и корректно ли система переходит между ними. Для успеха Первой итерации проекта считаем нижней границей 100%.
```math
\text{Workflow Correctness} =
\frac{\text{Количество успешно пройденных сценариев}}
{\text{Общее количество проверенных сценариев}}
```
>\* - Границы метрики для расценивания Первой итерации предварительные. Поскольку проект еще не вступил в разработку и не было выбрана модель LLM, следовательно сделать точные границы невозможно. В случае первой итерации самое главное - воспроизводимость и автономность. Мы хотим, чтобы система работала бесперебойно и стабильно выдавала предсказуемые ответы. Как только будут выбраны и протестированы все компоненты системы - будут и выбраны точные границы.


##### **Схема ML-валидации**
1. Разделить примеры на dev и test по `problem_id` (идентификатор задачи);
2. На dev подбирать шаблоны промптов, схему `Diagnosis`, температуру и политику уровней. Установить фиксированные версии модели/промптов, параметры генерации и ограниченный бюджет повторов.
3. Для каждой конфигурации сгенерировать подсказки при одинаковых входных данных и запустить Оффлайн оценку. При сравнении вариантов учитывать один и тот же набор примеров, стоимость и задержку.
4. Для test использовать конфигурацию, выбранную до просмотра test-результатов. Не донастраивать prompts или судью на итоговом test.
5. Экспертно просмотреть пограничные случаи и расхождения с LLM-as-a-Judge.

##### **Бейзлайн**
* **Предобработка:** Выделение необходимых сущностей, Отбор Python задач, Выделение двух выборок с задачами dev/test
* **Исполнение кода:** Sandbox (Judge0/др.);
* **Генерация подсказки:** Один вызов готовой LLM: условие + код + безопасная сводка проверки + заданный уровень -> подсказка + самопроверка;
* **Выбор уровня:** Фиксируется приложением и передаётся в prompt;
* **Переходы workflow:** Определяет код приложения по результату исполнения кода
* **Настройка:** Базовый prompt с запретом выдавать решение

##### **Стратегии дальнейшего развития решения**

**Первостепенные идеи развития:** улучшить формат исполнения/диагностических свидетельств и промпты' проверить раздельные операции `diagnose` и `generate_hint`; рассмотреть более подходящую модель или усовершенствовать constrained/structured output только после построения бейзлайна;

**Идеи, рассматриваемые после успешной реализации бейзлайна:**
1. Посторить RAG для поиска похожих задач (после решени задачи студенту предлагается рассмотреть задачи на схожую тему);
2. Реализация Суммаризации поведения студента. Пользователю предлагается составить отчет о том, как он справлялся с решением, где его слабые места, как он прогрессирует, на что стоит обратить внимание. Для реализации в теории возможно использовать БД для хранения информации по студентам и переодически обновлять сведения по мере использования системы пользователем.
